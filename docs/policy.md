# BRICK 프로젝트 정책

## 목적과 자료 위치

- `docs/gobricks-dictionary.json`은 부품 식별·판매·형상 참조 자료다. `assets/parts/`는 공용 형상이다. 판매 여부, 형상 일치, 조립 적합성, 실물 검증은 각각 구분한다.
- `docs/design-experience.json`에는 여러 모델에 재사용할 수 있고 근거가 확인된 설계 노하우만 둔다. 모델에만 해당하는 요구·실패·개선은 `models/<model>.md`에 둔다.
- 각 모델 버전의 유일한 원본은 `models/<model>-v<number>.mpd`다. MPD 내부 서브모델을 사용하고 별도 검토·진행 파일은 만들지 않는다. 버전별 범위와 예외는 해당 모델 기록에 둔다.
- `docs`의 공통 문서 세 개 외에 새 파일이나 폴더를 만들기 전에는 이름·목적·필요성을 사용자에게 보고하고 승인받는다. 새 모델 버전 MPD와 해당 모델 기록 갱신은 예외다.

## 역할과 병렬 작업

사용자가 별도로 실행한 여러 클라우드 에이전트가 같은 Git 저장소에서 서로 다른 모델을 개발한다. 메인 에이전트는 전체 조율·공통 자료 관리·통합과 사용자가 지시한 업무를 맡고, 개별 에이전트는 배정된 모델 개발을 맡는다. 별도 클라우드 에이전트 사이의 지시 전달과 작업 충돌 조율은 사용자가 수행한다. 메인 에이전트가 다른 클라우드 에이전트를 직접 지휘하거나 자동으로 변경을 전달한다고 가정하지 않는다.

- 개별 에이전트는 담당 모델·버전의 MPD와 기존 모델별 Markdown 기록을 갱신한다. 다른 담당자의 모델 파일은 수정하지 않는다. 같은 모델 기록을 여러 버전이 공유하므로 버전이 달라도 같은 파일의 동시 수정은 사용자와 조율한다. 설명서 구간은 담당 에이전트가 순서대로 진행한다.
- 공용 부품은 메인 에이전트가 우선 제작·등록한다. 개별 에이전트는 기존 공용 형상을 재사용하며, 오류나 수정사항을 발견하면 공용 형상과 그에 필요한 사전·에셋 목록을 직접 수정할 수 있다. 부품을 모델별로 복제하지 않는다. 신규 부품 파일이 필요한 경우에는 기존 파일 추가 전 보고 규칙을 따른다.
- 공용 부품을 수정할 때는 부품 번호·수정 이유·검증 결과·영향 범위를 커밋 설명과 작업 결과 보고에 남긴다. 관련 참조·사전·에셋 목록의 무결성을 함께 확인하고, 출처·라이선스와 검증 상태를 보존한다. 치수·원점·방향·연결 위치 변경처럼 다른 모델의 조립에 영향을 주는 수정은 사용자에게 알려 메인 에이전트의 통합 전 검토를 받는다.
- 모델 고유의 시행착오와 노하우는 기존 모델별 Markdown 기록에 남긴다. 공통 적용 후보는 문제·해결 방법·적용 조건·근거·검증 한계를 커밋 설명과 작업 결과 보고로 전달한다. 사용자가 해당 브랜치나 커밋을 알려주면 메인 에이전트가 확인하고 중복·모순을 검토해 기존 `docs/design-experience.json`에 통합한다. 개별 에이전트는 공통 경험 문서와 정책을 직접 수정하지 않는다. 검증된 팁은 공통 경험에 두고, 사용자 확정 지시와 필수 규칙만 정책에 둔다.
- 현재 체크아웃이 최신 `origin/main`보다 뒤처졌다는 이유만으로 작업을 중단하거나 환경 재게시·새 초안 로드를 요구하지 않는다. 로컬 변경과 현재 브랜치를 확인하고 자기 작업을 먼저 보존한 뒤, `git fetch origin`으로 최신 변경을 가져와 자신의 작업 브랜치에 병합하거나 로컬 커밋을 재배치한다. 공유된 브랜치의 이력을 임의로 재작성하지 않는다. 새 작업 브랜치가 필요하면 최신 `origin/main`에서 생성하고, 기존 브랜치에 작업이 있으면 이를 잃지 않도록 통합한다. 기존 체크아웃을 사용하며 별도 Git worktree나 관리 파일은 만들지 않는다.
- Git 파일 최신화와 클라우드 환경 게시·복원은 별개다. Git 최신화를 수행한 뒤에는 정책과 담당 모델 기록을 다시 읽고 원래 요청한 개발·검증을 계속한다. 실제 접근 오류나 의도를 판단할 수 없는 충돌만 구체적인 오류·영향 범위와 함께 질문하고, 막히지 않은 작업은 계속한다. Git 최신화를 이유로 기존 설계를 사용하지 말라는 지시 등 모델별 요구사항을 변경하지 않는다.
- 에이전트마다 별도 작업 브랜치를 사용한다. 작업 시작과 공유 변경 통합 전에 원격 최신 변경과 로컬 변경을 확인하고, 자기 작업을 보존한 뒤 관련 변경을 반영한다. 같은 공용 부품·사전·에셋 목록을 여러 에이전트가 동시에 수정하지 않도록 사용자가 조율한다. 별도 작업 브랜치만으로 같은 파일의 충돌이 방지된다고 가정하지 않는다.
- Git에는 자기 작업의 파일과 변경 구간만 선별해 반영한다. 다른 에이전트의 변경을 덮어쓰는 강제 푸시·일괄 되돌리기·무단 삭제를 하지 않는다. 충돌은 양쪽 의도를 확인해 해결하며, 다른 담당자의 설계 의도가 불명확하면 사용자와 조율한다. 공용 변경은 영향을 받는 모델을 검증한 뒤 통합한다. 개별 에이전트는 자기 작업을 검증하고 자신의 작업 브랜치에 커밋·원격 푸시한 뒤 브랜치명·커밋·검증 결과를 보고한다. 메인 에이전트가 변경을 검토해 `main`에 통합하고 최종 사이트 배포를 맡는다. 개별 에이전트는 `main`에 직접 푸시하거나 사이트를 배포하지 않는다. 클라우드 환경 게시를 코드 전달의 선행 조건으로 삼지 않으며, 환경 게시는 사용자의 별도 지시를 따른다.
- 별도 요청서·노하우 후보 파일·에이전트별 관리 파일·중복 진행 파일을 만들지 않는다. 모델별 기존 기록과 기존 공통 문서, Git 커밋 설명, 작업 결과 보고만 사용한다. 모델 기록에는 완료 범위·남은 검증·유용한 설계 근거만 남기고 대화 전문이나 단순 작업 일지를 쌓지 않는다. 새 관리 문서가 꼭 필요하면 먼저 사용자 승인을 받는다.
- 모델별 임시 MPD와 검토 복사본을 늘리지 않는다. 기존 임시 파일의 정리·삭제는 사용자 지시와 기존 파일 보존 규칙을 따른다. 새 모델 원본과 부품 형상 등 실제 개발 산출물은 기존 파일 추가 규칙을 따른다.

## 모델링 절차

1. 설명서나 요청 자료의 부품 종류·색상·수량을 먼저 식별한다. 사전과 공용 형상을 확인하고, 누락된 공용 모듈은 메인 에이전트에게 요청하고, 기존 부품 오류는 위 공용 부품 수정 규칙에 따라 직접 수정할 수 있다.
2. 각 부품의 좌표계와 실제 결합점을 확인한다. 중첩 서브모델의 변환은 안쪽부터 조립체까지 합성하고, 구멍 중심·축 방향·간격을 조립체 좌표로 비교한다. 그림의 원근이나 부품 원점만으로 접합 위치를 추측하지 않는다.
3. 축·핀은 양쪽 구멍의 중심과 방향뿐 아니라 삽입 범위도 확인한다. 층을 쌓을 때는 맞닿는 형상면과 스터드 높이를 기준으로 위치를 정한다.
4. 부품 식별이나 배치가 불확실하면 확인된 근거와 미해결 항목을 해당 모델 기록에 남기고, 가능한 다른 단계를 계속한다. 필수 연결을 임의로 확정하거나 생략하지 않는다.
5. GoBricks 미취급은 확인된 경우에만 `not_available_buy_lego`로 표시한다. 판매 여부가 확인되지 않았으면 `not_verified`로 둔다. 모델별 부품 제한은 해당 모델 기록을 따른다.
6. 계산상 정합, 시각적 접촉, 실제 삽입·간섭·고정력·하중, 실물 조립 검증을 구분해 기록한다. 도구 검사 통과만으로 조립 가능하다고 판정하지 않는다.

## 노하우와 완료 보고

- 재사용 가능한 방법은 문제, 적용 조건, 확인한 근거, 방법, 결과와 검증 한계를 기록한다. 성공이 확인되지 않은 추정은 검증된 노하우로 올리지 않는다.
- 담당 에이전트는 모델 고유 노하우를 해당 모델 기록에 갱신한다. 메인 에이전트는 커밋 설명과 작업 결과 보고로 전달받은 후보 중 근거를 검토한 공통 노하우만 `docs/design-experience.json`에 통합한다.
- 진행 보고에는 실제 확인한 페이지·단계, 반영한 부품 수, 미검증·미해결 항목을 구분해 적는다. 전체 범위를 대조하기 전에는 완료나 100% 구현이라고 말하지 않는다.
- 사용자가 질문하거나 상태를 물으면 먼저 답하고, 기존 작업은 명시적으로 중단·취소하라는 요청이 없는 한 이어간다. 사용자가 토론만 요청한 경우에는 파일을 수정하지 않는다.
- 개별 에이전트는 MPD·형상 참조·메타데이터와 적절한 검사를 확인해 자기 브랜치에 커밋·푸시한다. 메인 에이전트는 이를 검토·통합하고 필요한 검증 후 최종 배포한다. 작업 보고에서 브랜치 푸시 완료, `main` 통합 완료, 사이트 배포 완료를 구분한다.

## 공통 검증 범위

- 지원 MPD의 형상 참조·수량·좌표 변환은 `python3 tools/validate_model.py models/<model>-v<number>.mpd`로 검사한다. 도구가 지원하지 않는 스키마는 별도 구조 검사를 하고 한계를 보고한다.
- 뷰어 변경이 있는 경우에만 `cd viewer && npx playwright test`를 수행한다. 정적 사이트는 공개 시 모델·형상 자료도 내려받을 수 있음을 고려한다.
